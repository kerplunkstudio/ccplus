## Bug-Fix Chains Identified

### Chain 1: BYPASS_PERMISSIONS (3 commits)

1. `fix-config-bypass-permissions-hardcoded` (session) -> commit `4905291`: Changed hardcoded `const BYPASS_PERMISSIONS = true` to use `getBypassPermissions()` getter
2. `0d2533e` (separate session): Migrated config from DB to settings.json -- removed the `getBypassPermissions()` getter as part of the refactor
3. `68d742b` (manual fix): Restored `const BYPASS_PERMISSIONS = true` and removed obsolete getter references

**Root cause**: The fix session correctly identified and fixed the bug, but a concurrent refactor (`0d2533e`) was modifying the same file (`config.ts`) and removed the infrastructure the fix depended on. Neither session was aware of the other's changes. The result was wasted work -- the fix was committed, then undone, then manually restored.

**Lesson**: When Captain starts a bug-fix session targeting a shared module (config.ts, database.ts, server.ts), it should check for concurrent sessions modifying the same files. If found, it should either: (a) wait for the other session to complete, or (b) note the dependency in the session prompt.

### Chain 2: Fleet Agent Count Display (3 iterations)

1. `eaa1335` (pre-v2 fix): Changed display from totalAgents to activeAgents, added `activeAgents` to FleetSession type
2. `fix-fleet-dashboard-agent-count-tracking-v2` (session) -> commit `47ea799`: Added conditional logic (show activeAgents for running, totalAgents for completed)
3. `a2eba4c` (follow-up): Simplified to always show totalAgents

**Root cause**: The v2 session over-engineered the fix. It added conditional display logic (activeAgents for running sessions, totalAgents for terminal sessions) when the user ultimately wanted the simplest approach: always show totalAgents. The session followed the debugger's recommendation without questioning whether the conditional approach was the right one.

**Lesson**: Bug-fix sessions should prefer the simplest possible fix. Adding conditional branching when a simpler approach exists is a common anti-pattern. The code_agent and debugger should be reminded of the "smallest reasonable fix" principle, especially for UI display bugs.

## Cross-Session Patterns

### Pattern 1: False "failed" status (5/5 sessions)

All sessions show as "failed" despite completing their work. This is likely a status tracking bug in the fleet monitor where the merge/cleanup phase failure marks the entire session as failed. This makes retrospective analysis unreliable and could trigger unnecessary retry sessions.

**Recommendation**: Investigate the fleet session status tracking to ensure sessions that successfully commit and merge are marked as "completed" even if post-merge cleanup fails. Consider adding a "merged" status that is set before cleanup begins.

### Pattern 2: Over-engineering bug fixes (2/5 sessions)

Both `fix-fleet-dashboard-agent-count-tracking-v2` and `fix-config-bypass-permissions-hardcoded` added more complexity than needed. The agent count fix added conditional branching that was later simplified. The config fix introduced a getter pattern that was incompatible with a concurrent refactor.

**Recommendation**: Reinforce "smallest reasonable fix" in the debugger agent prompt. Add guidance to prefer adding/modifying behavior at the callsite over introducing new indirection (getters, factories, conditionals).

### Pattern 3: Concurrent modification of shared modules (1/5 sessions)

The config.ts file was modified by two concurrent sessions, with one undoing the other's work. No coordination mechanism detected this.

**Recommendation**: Captain should check `files_touched` of active sessions before starting a new session on the same files. If overlap is found, queue the session or include the dependency in the prompt.

### Pattern 4: Research-to-feature pipeline works well (2/5 sessions)

The research -> context-tracking pipeline worked cleanly. Research produced a doc, feature session consumed it. This is a validated workflow pattern.
